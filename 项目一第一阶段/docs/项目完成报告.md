## 摘要

本实验设计并实现了一个简化版在线问卷系统，功能包括用户注册登录、问卷创建与发布、9 种题型管理、条件跳转、链接分享、匿名或登录填写、草稿保存、答案校验、统计分析和多格式导出。系统采用 Flask 分层架构，使用 MongoDB 的四个集合分别存储用户、问卷、题目和回答，通过 ObjectId 建立关联，并把题型规则、校验规则和跳转规则保存在题目文档中，避免将业务规则写死在代码里。

项目重点解决了三个问题：一是用文档模型表达动态题型和动态答案；二是用统一的数据结构描述条件跳转，并在填写、校验、统计三个阶段保持一致；三是建立“浏览器约束—前端校验—后端兜底”的三层校验机制。开发过程中使用 AI 编程助手生成项目骨架、重复性代码、前端初稿和测试草稿，本人负责总体设计、关键交互取舍、运行验收和问题修正。最终 8 个测试文件共 71 个测试全部通过。

## 1. 项目目标

### 1.1 实验目的

本实验以“在线问卷系统”为载体，重点训练以下能力：

3. 将题型、校验规则和跳转逻辑抽象为可配置数据，而不是写死在代码中。

5. 使用 pytest 和 mongomock 建立自动化测试，验证核心业务规则。
6. 规范使用 AI 编程工具：由本人提出需求、审查结果、运行测试并修正问题，而不是直接复制 AI 输出。

## 2. 系统设计

### 2.1 技术选型

| 层次 | 技术 | 选择理由 |
|------|------|----------|
| 后端框架 | Flask 3.0 | 轻量、路由清晰，适合课程项目快速迭代 |
| 数据库 | MongoDB 8.3 | 题型、选项、答案和跳转规则都是动态结构，文档模型比固定表结构更自然 |
| 身份认证 | Flask-JWT-Extended | 前后端分离场景下使用 Bearer Token，便于区分登录与匿名访问 |
| 前端 | 原生 HTML/CSS/JavaScript | 不引入额外构建链，便于直接由 Flask 托管和调试 |
| 图表 | Chart.js | 实现每日趋势、选项分布和数值分布图 |
| 测试 | pytest + mongomock | 不依赖真实 MongoDB 即可测试服务层和 API 层 |

### 2.2 总体架构

系统采用“路由层—服务层—模型层”的分层结构，前端通过统一 API 与后端通信：

```
┌──────────────────────────────────────────────┐
│ 前端页面：登录 / 问卷管理 / 创建 / 编辑 / 填写 / 统计 │
└───────────────────────┬──────────────────────┘
                        │ HTTP + JSON + JWT
┌───────────────────────▼──────────────────────┐
│ 路由层 app/routes：参数接收、认证、响应封装          │
├──────────────────────────────────────────────┤
│ 服务层 app/services：业务规则、校验、跳转、统计       │
├──────────────────────────────────────────────┤
│ 模型层 app/models：集合操作、查询、索引相关字段        │
├──────────────────────────────────────────────┤
│ MongoDB：users / surveys / questions / responses │
└──────────────────────────────────────────────┘
```

| 层 | 职责 | 代表文件 |
|----|------|----------|
| 路由层 | 接收请求、读取 JWT、调用服务、返回统一 JSON | `app/routes/*.py` |
| 服务层 | 状态机、权限、跳转、校验、提交、统计 | `app/services/*.py` |
| 模型层 | 文档构造、CRUD、按条件查询、题目排序 | `app/models/*.py` |
| 工具层 | 统一响应、邮箱等通用校验 | `app/utils/*.py` |
| 前端层 | 表单渲染、交互状态、前端校验、图表展示 | `frontend/*.html` |

### 2.3 模块划分

| 模块 | 主要职责 |
|------|----------|
| 认证模块 | 注册、登录、当前用户信息、密码哈希、JWT 生成 |
| 问卷模块 | 问卷 CRUD、状态转换、链接码、截止时间、公开列表 |
| 题目模块 | 题目 CRUD、批量添加、排序、限制条件、跳转条件 |
| 跳转服务 | 条件判断、可见性计算、下一题计算、旧答案过滤 |
| 校验服务 | 按题型执行必填、选项、长度、范围、数量等校验 |
| 填写模块 | 开始填写、草稿保存、校验预览、提交、匿名与限填控制 |
| 统计模块 | 聚合统计、单题统计、每日趋势、导出 |
| 前端模块 | 页面渲染、动态题目卡片、折叠配置卡片、错误提示、图表 |

### 2.4 核心业务流程

1. 用户注册并登录，后端返回 JWT。
2. 用户创建问卷，填写标题、描述、截止时间和匿名/限填等设置。
3. 用户在创建页添加题目，配置选项、必填、限制条件和跳转逻辑。
4. 问卷至少有一道题时才能发布；发布后生成 8 位 `link_code`。
5. 填写者通过 `/survey/<link_code>` 打开问卷；系统检查发布状态、截止时间、匿名设置和限填规则。
6. 填写过程中保存草稿；点击下一题或提交时执行前端校验，并按跳转规则计算下一题。
7. 提交时后端重新读取题目和答案，执行全量校验，过滤被隐藏或跳过题目的旧答案，再写入 `submitted` 状态。
8. 创建者在统计页查看总览、趋势、单题分布，并导出 JSON/CSV/Excel。

### 2.5 API 与响应设计

后端共 27 个路由入口，按四个蓝图分组：

- `/api/auth/*`：注册、登录、当前用户。
- `/api/surveys/*`：问卷、题目、发布、关闭、公开链接。
- `/api/fill/*`：开始填写、草稿、校验、提交。
- `/api/stats/*`：问卷统计、单题统计、导出。

响应统一为：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

错误响应使用对应 HTTP 状态码，并在 `message` 中给出可读原因；提交校验失败时，`data` 中返回以题目 ID 为键的错误信息，便于前端定位到具体题目。

### 2.6 权限与安全设计

- 密码使用 Werkzeug 的 `generate_password_hash` 存储，不保存明文。
- 创建、修改、发布、关闭、删除问卷时校验 `creator_id`，防止越权操作。
- 已发布问卷禁止修改基本信息和题目，避免填写过程中结构变化。
- 公开链接只返回已发布且未截止的问卷。
- 匿名填写通过 `settings.allow_anonymous` 控制；`one_per_user` 通过回答记录检查。
- 邮箱收集开启时，前后端都校验格式。
- 非法 ObjectId 统一按“不存在”处理，避免 500。

### 2.7 前端交互设计

前端采用单页内的动态渲染方式：题目数据保存在 JavaScript 数组中，修改后重新渲染题目卡片。为了降低误操作，创建页和编辑页将“跳转逻辑”和“限制条件”做成可折叠卡片，并设置独立保存按钮：字段变化先进入草稿，点击保存后才写入正式配置；存在未保存草稿时，整卷保存会被拦截。填写页按题目的 `validation` 和 `jump_logic` 动态生成输入控件、限制提示和下一题行为。

## 3. MongoDB 设计

### 3.1 设计原则

本系统在 MongoDB 建模时遵循三条原则：

1. **按领域拆分集合**：用户、问卷、题目、回答分别存储，避免把所有数据塞进一个文档。
2. **谨慎使用冗余**：题目定义与回答数据分离，回答中只保存 `question_id -> answer`，不复制题目标题、选项等元数据。
3. **规则数据化**：题型、校验规则、跳转规则都放在 `questions` 文档中，由服务层读取并解释，新增题型或规则时尽量不改业务主流程。

### 3.2 集合结构

| 集合 | 作用 | 主要字段 |
|------|------|----------|
| `users` | 用户账号与认证 | `_id`, `username`, `email`, `password_hash`, `role`, `is_active`, `created_at`, `updated_at` |
| `surveys` | 问卷元数据与全局设置 | `_id`, `title`, `description`, `creator_id`, `status`, `settings`, `deadline`, `link_code`, `published_at`, `closed_at` |
| `questions` | 问卷中的题目定义 | `_id`, `survey_id`, `title`, `type`, `order`, `required`, `options`, `validation`, `jump_logic` |
| `responses` | 一次填写记录 | `_id`, `survey_id`, `user_id`, `answers`, `status`, `started_at`, `submitted_at`, `ip_address`, `user_agent`, `email` |

其中：

- `surveys.status` 取值为 `draft`、`published`、`closed`。
- `responses.status` 取值为 `in_progress`、`submitted`。
- `surveys.settings` 内嵌 `allow_anonymous`、`show_progress`、`one_per_user`、`collect_email`。
- `responses.user_id` 在匿名填写时为 `null`。
- `responses.email` 仅在问卷开启“收集邮箱”且填写者提供时保存。

### 3.3 集合关系

```
users (1) ──────< (N) surveys
surveys (1) ────< (N) questions
surveys (1) ────< (N) responses
users (1) ──────< (N) responses
questions (1) ──< (N) responses（通过 answers 的键关联）
```

系统采用“引用式”关系：`surveys.creator_id`、`questions.survey_id`、`responses.survey_id`、`responses.user_id` 保存 ObjectId。题目与回答之间不建立显式外键，而是用 `answers` 对象中的题目 ID 字符串作为键。

### 3.4 索引设计

| 集合 | 索引 | 用途 |
|------|------|------|
| `users` | `username` 唯一 | 登录、注册查重 |
| `users` | `email` 唯一且稀疏 | 邮箱查重，兼容早期无邮箱数据 |
| `surveys` | `creator_id` | 查询“我的问卷” |
| `surveys` | `status` | 筛选草稿、已发布、已关闭 |
| `surveys` | `link_code` 唯一 | 分享链接访问 |
| `questions` | `survey_id` | 按问卷读取题目 |
| `responses` | `(survey_id, user_id)` 复合 | 检查重复填写和恢复草稿 |
| `responses` | `submitted_at` | 按提交时间排序和趋势统计 |

题目的显示顺序由 `order` 字段控制，查询时执行 `sort('order', 1)`。当前数据规模下该方式足够；如果题目数量继续增长，可以再增加 `(survey_id, order)` 复合索引。

### 3.5 动态字段设计

#### （1）校验规则 `validation`

不同题型使用不同字段，服务层按题型读取：

```javascript
// 多选题：以下三种规则互斥
{ "min_select": 2 }          // 至少选择 2 个
{ "max_select": 3 }          // 最多选择 3 个
{ "exact_select": 2 }        // 必须选择 2 个

// 文本题
{ "min_length": 10, "max_length": 200, "pattern": "^[A-Za-z]+$" }

// 数字题
{ "min": 0, "max": 100, "integer_only": true }

// 评分题
{ "min": 1, "max": 5 }
```

#### （2）跳转规则 `jump_logic`

```javascript
{
  "source_question_id": "源题目ID",
  "condition": "equals",
  "value": "选项A",
  "target_question_id": "目标题目ID",
  "action": "skip_to"
}
```

#### （3）回答对象 `answers`

```javascript
{
  "题目ID_1": "选项A",
  "题目ID_2": ["选项A", "选项C"],
  "题目ID_3": "用户填写的文本",
  "题目ID_4": 42,
  "题目ID_5": "2026-10-18"
}
```

答案类型由题型决定：选择题为字符串或数组，文本题为字符串，数字和评分为数值，日期为 `YYYY-MM-DD` 字符串，文件题为文件名或地址字符串。

### 3.6 为什么适合使用 MongoDB

1. **结构动态**：9 种题型的选项、校验字段和答案格式不同，文档模型不需要为每种题型建表。
2. **嵌套自然**：问卷设置、题目限制、跳转条件和回答对象都可以作为嵌套文档保存。
3. **数组支持好**：选择题选项和多选题答案直接使用数组。
4. **聚合能力合适**：每日趋势、选项分布、数值分布可以借助 `$match`、`$group`、`$dateToString` 完成。
5. **生命周期独立**：题目定义与回答快照分离，修改题目不会破坏历史回答。

## 4. 跳转设计

### 4.1 跳转规则的数据结构

跳转规则保存在 `questions.jump_logic` 中，一条规则由“源题目、条件、比对值、目标题目、动作”组成：

```json
{
  "source_question_id": "源题目ID",
  "condition": "equals | not_equals | contains | greater_than | less_than",
  "value": "比对值",
  "target_question_id": "目标题目ID",
  "action": "skip_to | hide | show"
}
```

将规则存入数据库而不是写死在代码中，好处是：创建者可以在页面上配置不同逻辑，服务层只负责解释规则；新增条件类型时只需扩展判断函数。

### 4.2 条件与动作语义

| 条件 | 判断方式 |
|------|----------|
| `equals` | 答案字符串等于比对值 |
| `not_equals` | 答案字符串不等于比对值 |
| `contains` | 数组包含比对值，或字符串包含比对值 |
| `greater_than` | 转为数值后大于比对值 |
| `less_than` | 转为数值后小于比对值 |

| 动作 | 含义 |
|------|------|
| `skip_to` | 条件满足时跳过中间题目，直接到目标题目 |
| `hide` | 条件满足时隐藏配置该规则的题目 |
| `show` | 条件满足时显示配置该规则的题目（默认隐藏） |

### 4.3 填写时的运行算法

1. 按 `order` 对题目升序排序，得到题目序列。
2. 遍历题目，根据 `hide`/`show` 规则计算当前题目是否可见。
3. 当前题作答后，若其 `jump_logic.action` 为 `skip_to`，判断条件是否成立；成立时返回目标题目作为下一题。
4. 若没有触发跳转，则从当前题目向后寻找下一道可见题目。
5. 提交时重新推演整份问卷，收集被跳过的题目 ID，并从最终答案中删除这些题目的旧答案，避免“用户先填了题目，后来被跳转跳过，旧答案仍被保存或统计”的问题。

实现位于 `app/services/jump_service.py` 和 `ValidationService._get_skipped_ids()`。

### 4.4 边界处理

| 场景 | 处理方式 |
|------|----------|
| 目标题目在当前题目之前 | 配置界面禁止；提交推演时忽略反向目标，防止循环 |
| 目标题目不存在 | 忽略该跳转，按默认下一题处理 |
| `hide`/`show` 动作 | 只影响题目可见性，不参与“下一题”跳转，避免指向自身时原地循环 |
| 旧数据保存的是题目顺序而不是 ID | 查找时兼容按 `order` 匹配 |
| 隐藏或跳过题目的旧答案 | 提交前统一过滤，不写入数据库、不参与统计 |
| 源题目未作答 | 不触发跳转，按默认顺序继续 |

### 4.5 配置界面设计

创建页和编辑页的跳转配置采用折叠卡片：

- 选择源题目后，根据源题型生成“比对值”控件：单选/下拉显示选项下拉框，多选显示多选控件，文本和数字保留输入框。
- 修改源题目时，清空不再适用的旧比对值，避免保存无效组合。
- 卡片展开状态单独记录，选择源题目或修改条件时不会自动收起。
- 字段变化先进入 `_jumpDraft`，点击“保存跳转逻辑”后才写入正式配置；编辑页对已有题目立即调用题目更新接口持久化。
- 保存前检查源题目、条件、比对值、目标题目和动作是否完整，存在未保存草稿时阻止整卷保存。

## 5. 校验设计

### 5.1 三层校验

系统把校验拆成三层，避免只依赖前端或只依赖后端：

| 层次 | 触发时机 | 作用 |
|------|----------|------|
| 浏览器约束 | 输入时 | 通过 `required`、`minlength`、`maxlength`、`min`、`max`、`step` 等属性提供即时反馈 |
| 前端业务校验 | 点击“下一题”或“提交”时 | 校验必填、多选数量、文本长度、数字范围、整数要求；不通过时阻止前进并显示错误 |
| 后端全量校验 | 提交接口 | `ValidationService.validate_all()` 重新读取题目和答案，逐题校验，防止绕过前端 |

后端校验是最终依据。即使前端被修改或有人直接调用 API，提交时仍会按数据库中的规则重新判断。

### 5.2 各题型校验规则

| 题型 | 答案格式 | 校验内容 |
|------|----------|----------|
| `single_choice` | 字符串 | 必填；答案必须在 `options` 中 |
| `multiple_choice` | 数组 | 必填；每个元素必须在 `options` 中；支持 `min_select`、`max_select`、`exact_select` |
| `dropdown` | 字符串 | 同单选 |
| `text` / `textarea` | 字符串 | 必填；`min_length`、`max_length`、`pattern` |
| `number` | 数值 | 必填；`min`、`max`、`integer_only` |
| `rating` | 数值 | 必填；`min`、`max` 范围 |
| `date` | 字符串 | 必填；`YYYY-MM-DD` 格式 |
| `file` | 字符串 | 必填；非空字符串 |

### 5.3 多选题数量限制设计

本人在需求分析中将多选题限制归纳为三种互斥规则：

| 规则 | 含义 | 示例 |
|------|------|------|
| `min_select` | 至少选择 N 个 | 至少选择 2 个 |
| `max_select` | 最多选择 N 个 | 最多选择 3 个 |
| `exact_select` | 必须选择 N 个 | 必须选择 2 个 |

规则语义如下：

1. `exact_select` 优先于 `min_select` 和 `max_select`；配置界面禁止三者同时出现，避免规则冲突。
2. 配置了 `exact_select` 或 `min_select > 0` 时，空答也不满足要求，即使题目没有勾选“必填”。
3. 只配置 `max_select` 时，空答允许跳过，因为“最多”不构成最低作答要求。
4. 数量不能超过选项总数；前端在保存限制条件时检查，后端在提交时按实际答案检查。
5. 前端对限制值做数值化防御，只有“大于等于 1 的整数”才生效。

后端逻辑位于 `ValidationService.validate_answer()`：空答先判断必填，再判断多选的 `exact/min`；非空答先校验选项合法性，再校验数量。前端在 `create.html`、`edit.html` 中保存限制条件时校验规则本身，在 `survey.html` 中校验用户答案。

### 5.4 文本与数字校验

- 文本题：最少字数、最多字数和正则表达式。填写页为输入框设置 `minlength`、`maxlength`，提交前再提示具体长度要求。
- 数字题：最小值、最大值和“仅允许整数”。填写页设置 `min`、`max`、`step=1`，前端检查是否为整数，后端再次检查类型和范围。
- 评分题：按 `min`、`max` 控制评分范围。

限制条件在创建页和编辑页中使用与跳转逻辑一致的折叠卡片：字段变化先写入 `_validationDraft`，点击“保存限制条件”后才写入 `validation`；编辑页对已有题目立即持久化，创建页提示“保存问卷后生效”；存在未保存草稿时，整卷保存会被拦截。

### 5.5 跳转与校验的配合

校验不是简单遍历全部题目，而是与跳转逻辑配合：

1. 先根据答案推演问卷，得到被隐藏或跳过的题目集合。
2. `validate_all()` 跳过这些题目的必填和格式校验。
3. 提交时调用 `get_effective_answers()`，只保留实际展示过且未被跳过的答案。
4. 这样既不会要求用户回答被跳过的题目，也不会把旧答案写入统计。

### 5.6 错误返回

校验失败时返回 HTTP 422，`data` 为题目 ID 到错误信息的映射：

```json
{
  "code": 422,
  "message": "校验失败",
  "data": {
    "题目ID": "至少需要选择 2 个选项"
  }
}
```

前端根据题目 ID 把错误显示在对应题目卡片下方；下一题和提交都会先执行同一套前端检查。

## 6. AI 使用过程

### 6.1 使用方式

本项目使用 VS Code 中的 AI 编程助手（Kilo/Cline）进行结对辅助。本项目将 AI 定位为“结对编程助手”，而不是替代设计者。实际过程是：

1. 本人先拆分需求，确定数据模型、页面流程、跳转语义和校验规则。
2. 按模块向 AI 描述任务，要求它生成可运行的代码、测试和文档初稿。
3. 本人运行 `pytest`、检查接口返回、在浏览器中走完整流程。
4. 发现不一致时，定位是数据模型、接口路径、前端事件还是业务语义问题，再做局部修正。
5. 把关键修正、原因和验证结果记录到 `docs/AI使用日志.md`，当前共 68 条记录。

使用 AI 的原则是：**可以生成，但必须验证；可以借鉴，但设计要自己确认。** 尤其是跨文件契约、表单事件、跳转状态和校验语义，不能只看 AI 的说明，必须以实际运行结果为准。

### 6.2 AI 帮了什么

- 按照本人确定的分层结构，快速生成项目目录、配置、Flask 应用工厂和四个 MongoDB 模型的基础代码。
- 生成认证、问卷、题目、填写、统计等服务层和路由层初稿，减少重复 CRUD 的编写时间。
- 生成 7 个前端页面的布局、表单、动态题目卡片和 Chart.js 图表初稿。
- 生成 8 个测试文件及 `conftest.py`，覆盖认证、CRUD、跳转、校验、提交和统计。
- 生成数据库设计、API 说明、测试用例、关键逻辑说明等文档初稿。
- 在出现报错时提供排查方向，例如 405、网络错误、MongoDB 模拟和测试夹具问题。
- 把本人确定的设计快速落到代码，使项目能在较短时间内形成可运行版本。

### 6.3 AI 做错了什么

AI 的初稿并非一次正确。以下是开发过程中比较典型的问题：

1. **模型构造参数遗漏**：`Survey.__init__()` 初版没有 `settings` 参数，创建问卷时传入设置会报错。本人补上参数并合并默认设置。
2. **导入和测试夹具不完整**：`user_service.py` 缺少 `Dict` 导入；跳转测试的 `FakeQuestion` 缺少 `order`；部分测试的 `jump_logic` 嵌套层级与服务层不一致。本人按报错补齐导入、属性和测试数据结构。
3. **MongoDB 客户端无法被测试替换**：初版直接 `from pymongo import MongoClient`，导致测试中 patch 目标不正确。本人改为 `import pymongo` 并通过 `pymongo.MongoClient` 访问。
4. **前端按钮默认提交表单**：动态生成的“跳转逻辑”“上移/下移”“删除题目”等按钮没有写 `type`，默认是 `submit`，点击后会意外提交表单；编辑页还会丢失地址栏中的 `?id=`。本人统一补 `type="button"`，增加表单提交拦截和 ObjectId 校验。
5. **接口路径不一致**：编辑页更新题目时调用了 `/api/questions/<id>`，而后端实际路径是 `/api/surveys/questions/<id>`，导致 405。本人按蓝图前缀修正前端请求。
6. **保存按钮不在表单内**：编辑页的保存按钮位于导航栏，点击不会触发表单的 `submit` 事件。本人把保存逻辑绑定到按钮的 `click` 事件。
7. **跳转卡片状态丢失**：选择源题目后页面重新渲染，卡片被自动收起，半填写的条件也可能被清空。本人引入独立的展开状态和草稿字段，保留用户正在编辑的内容。
8. **在线地址与网络错误**：前端初版直接用 `location.origin` 拼接 API，使用 Live Server 打开页面时请求发到了静态服务器，显示“网络错误”。本人统一 API 基址判断，补充后端 `/frontend/*` 兼容路由和 README 排查步骤。
9. **校验规则不完整**：AI 初版只实现了多选题的 `min/max`，没有“必须选择数”；空答时也可能直接放行 `min_select`。本人在验收中补充 `exact_select`、空答语义、前后端校验和单元测试。
10. **文档统计口径不一致**：初版文档把完成率写成“始终 100%”，与代码实际按“已提交/已开始”计算不一致。本人按代码口径修正文档，并同步测试数量。

上述问题说明：AI 很擅长生成“看起来完整”的代码，但对跨文件契约、浏览器表单行为和业务边界的理解需要人工复核。

### 6.4 自己改了什么

本人没有大改现有工程结构，主要是在运行和验收阶段做局部修正：

- 修正模型构造参数、类型导入、测试夹具和 MongoDB 模拟方式，让项目能稳定启动和测试。
- 修正前端按钮类型、表单提交、题目更新路径和保存按钮事件，消除误提交、405 和“点击无反应”。
- 统一前端 API 基址和网络错误提示，补充 README 中的排查步骤。
- 修正跳转卡片的展开状态和草稿保留逻辑，避免配置过程中丢失已填内容。
- 补齐多选题的“必须选择数”和空答语义，补充对应单元测试，确保前后端口径一致。
- 校正文档中的测试数量、完成率口径和部分过时说明。

这些修改以“小步定位、单点修复、回归测试”为主，没有改变四集合结构、分层架构和主要页面流程。它们更多是本人作为项目负责人对 AI 初稿进行的验收性微调。

### 6.5 自己设计了什么

项目的主要设计由本人确定，AI 负责生成实现初稿：

1. **总体功能边界**：确定用户、问卷、题目、填写、统计五个模块，以及 9 种题型和 7 个页面。
2. **MongoDB 四集合模型**：确定 `users`、`surveys`、`questions`、`responses` 的职责边界、字段和索引，坚持题目与回答分离。
3. **问卷状态机**：设计 `draft → published → closed` 的转换规则，只有草稿可编辑，只有已发布可通过链接填写。
4. **跳转规则模型**：确定“源题目 + 条件 + 比对值 + 目标题目 + 动作”的统一结构，以及 `skip_to`、`hide`、`show` 三种语义。
5. **校验体系**：设计浏览器约束、前端校验、后端兜底三层结构；把多选题限制归纳为 `min/max/exact`，并确定空答和互斥规则。
6. **配置交互**：将跳转和限制条件设计为折叠卡片，采用“草稿 + 独立保存 + 整卷保存拦截”的方式，减少误操作。
7. **填写流程**：设计 `in_progress → submitted`、草稿恢复、匿名/登录双模式、限填一次、跳过题答案过滤。
8. **统计与导出**：确定回答数、完成率、平均耗时、每日趋势、单题分布和 JSON/CSV/Excel 导出。
9. **验收标准**：把关键规则拆成 71 个自动化测试，并补充浏览器手工验收清单。

### 6.6 AI 使用反思

- AI 最适合做“有明确边界的重复劳动”，例如 CRUD、页面骨架、测试模板和文档初稿。
- AI 最容易出错的地方是跨文件一致性：前端路径与后端蓝图、字段名与模型构造、文档描述与实际代码。
- 让 AI 生成代码后，必须自己运行测试和浏览器流程；仅阅读代码或相信总结不足以发现问题。
- 提问时应给出明确约束，例如“必须与现有 `ValidationService` 的返回格式一致”“修改后运行 pytest 和 node --check”，并要求 AI 说明修改了哪些文件。
- 保留 AI 使用日志很有价值，既能追溯问题，也能在报告中如实说明哪些是 AI 生成、哪些是本人修正。

## 8. 遇到的问题

### 8.1 环境与测试问题

| 问题 | 现象/影响 |
|------|-----------|
| Windows 版 MongoDB 不支持 `--fork` | 按 Linux 方式启动失败，需要以前台进程或后台进程方式运行 |
| `pymongo.MongoClient` 难以被测试替换 | patch 目标与实际导入方式不一致，测试无法隔离数据库 |
| Live Server 打开页面时接口请求错误 | 请求被发到静态服务器，返回 HTML，前端解析 JSON 失败并提示“网络错误” |
| 前端资源路径不统一 | 直接访问 `/frontend/xxx.html` 与 Flask 静态目录不一致，需要兼容路由 |

### 8.2 数据模型与业务问题

| 问题 | 现象/影响 |
|------|-----------|
| `Survey` 构造参数缺少 `settings` | 创建问卷传入设置时报 `TypeError` |
| 截止时间的时区处理不统一 | 浏览器本地时间与 UTC 比较可能偏差，导致提前或延迟截止 |
| 重复打开填写页产生多条草稿 | 同一用户可能有多条 `in_progress` 记录 |
| 平均耗时直接在 MongoDB 聚合中计算 | 日期嵌套聚合存在兼容性问题，部分环境结果异常 |
| 文档把完成率写成 100% | 与实际“已提交/已开始”的计算口径不一致 |

### 8.3 前端交互问题

| 问题 | 现象/影响 |
|------|-----------|
| 动态按钮默认为 `submit` | 点击跳转、排序、删除题目时意外提交表单 |
| 编辑页表单提交导致地址栏参数丢失 | 页面请求 `/api/surveys/null`，出现 500 或空白 |
| 题目更新接口路径错误 | 前端请求 `/api/questions/<id>`，后端实际为 `/api/surveys/questions/<id>`，返回 405 |
| 保存按钮不在 `<form>` 内 | 点击“保存修改”没有反应，因为不会触发表单 submit |
| 跳转卡片重新渲染后自动收起 | 用户选择源题目后，半填写的条件丢失或需要重新展开 |
| 多选限制输入不完整 | 初版只有最少/最多，缺少“必须选择数”；空答语义不清晰 |

### 8.4 跳转与校验问题

| 问题 | 现象/影响 |
|------|-----------|
| `hide`/`show` 被误当成下一题跳转 | 目标指向自身时可能原地循环 |
| 旧数据的跳转引用保存的是 `order` | 直接按 ObjectId 查找不到源题目或目标题目 |
| 被跳过题目的旧答案仍被提交 | 统计结果包含用户实际没有看到的题目答案 |
| 多选题空答直接放行 | 配置“至少选择”或“必须选择”时，空答不符合业务要求 |
| 校验规则前后端不一致 | 前端拦截但后端可通过，或反之，造成体验和安全性问题 |

### 8.5 文档与协作问题

| 问题 | 现象/影响 |
|------|-----------|
| 测试数量更新不及时 | 文档测试数量一度落后于实际用例数 |
| AI 生成说明与实际代码不一致 | 例如完成率、接口路径、字段层级 |
| 跨文件修改容易遗漏 | 后端改了路径，前端未同步；模型改字段，测试未同步 |
| AI 生成代码需要反复验收 | 看起来完整，但运行后才暴露事件、路径和数据语义问题 |

---

## 9. 如何解决

### 9.1 定位方法

1. **先复现**：记录页面地址、请求 URL、HTTP 状态码、控制台错误和后端日志。
2. **缩小范围**：用最小请求或最小测试复现，不直接在完整页面里猜原因。
3. **对照契约**：比较前端请求路径、字段名、返回格式与后端路由、服务层参数是否一致。
4. **补测试**：修复后补充或调整测试，避免同类问题再次出现。
5. **回归验证**：运行 `pytest tests/ -q`，对前端脚本执行 `node --check`，再走一遍浏览器流程。
6. **同步文档**：把测试数量、接口路径和业务口径同步到文档与 AI 使用日志。

### 9.2 具体解决方案

| 问题 | 解决方法 |
|------|----------|
| MongoDB 启动参数 | 在 Windows 下使用前台进程或后台进程启动，不使用 `--fork` |
| 测试数据库隔离 | 改为 `import pymongo`，通过 `pymongo.MongoClient` 访问，便于 patch 和 mongomock 替换 |
| 网络错误 | 统一 API 基址：5000 端口使用同源 `/api`，其他端口请求 `http://<host>:5000/api`；补充 `/frontend/*` 兼容路由 |
| `settings` 缺失 | 为 `Survey.__init__()` 增加 `settings=None`，合并 `DEFAULT_SETTINGS` |
| 时区问题 | 截止时间统一解析为 UTC naive datetime，输出时补 `Z`，前端按本地时区展示 |
| 重复草稿 | 开始填写时优先复用同一用户同一问卷的 `in_progress` 记录；`one_per_user` 再检查 `submitted` |
| 平均耗时 | 在 Python 端根据 `started_at`、`submitted_at` 计算，避免复杂日期聚合兼容性问题 |
| 误提交和丢失 ID | 动态按钮统一 `type="button"`；表单阻止默认提交；编辑页校验 24 位 ObjectId |
| 405 题目更新 | 前端改为 `/api/surveys/questions/<id>`，与 `survey_bp` 的 `/api/surveys` 前缀一致 |
| 保存按钮无反应 | 保存逻辑绑定到按钮 `click` 事件，不再只依赖表单 `submit` |
| 跳转卡片收起 | 用 `_jumpOpen` 记录展开状态；用 `_jumpDraft` 保存半填写条件；独立保存后才写入 `jump_logic` |
| 多选数量规则 | 增加 `exact_select`，明确其与 `min/max` 互斥；空答时 `exact/min` 拦截、仅 `max` 放行；前端和后端同步 |
| 被跳过答案 | 提交时推演跳转，收集 `skipped`，用 `get_effective_answers()` 过滤旧答案 |
| 文档不一致 | 以代码和测试结果为准，更新测试数量、完成率和接口说明 |

### 9.3 预防措施

- **先定契约再写代码**：路由前缀、请求字段、返回结构和错误格式先确定，前后端按同一契约实现。
- **校验分层**：浏览器约束只做体验，前端业务校验做即时反馈，后端校验做最终兜底。
- **小步修改**：每次只改一个模块或一个问题，改完立即运行相关测试，避免多个问题混在一起。
- **AI 输出必须复核**：重点检查跨文件引用、路径、字段名、事件绑定和空值边界。
- **测试即文档**：测试名称直接描述业务规则，例如“多选题必须选择数”“跳过题答案不落库”。
- **日志可追溯**：记录每次 AI 修改的文件、原因、验证结果和遗留问题，方便回滚和写报告。

## 10. 总结与展望

### 10.1 项目总结

本项目完成了一个可运行的在线问卷系统，覆盖从用户认证、问卷创建、题目配置、条件跳转、链接分发、填写提交到统计导出的完整闭环。系统使用 MongoDB 四集合模型表达动态问卷结构，使用 JWT 处理登录与匿名访问，使用统一的服务层实现状态机、跳转、校验和统计。

在实现过程中，本人重点把握了以下设计：

- 题目定义与回答数据分离，避免题目修改破坏历史回答。
- 跳转规则和校验规则数据化，由服务层动态解释。
- 前端体验与后端安全兼顾，提交时始终以后端校验为准。
- 用测试固定关键规则，尤其是跳转、空答、多选数量和跳过题答案过滤。

AI 在项目骨架、重复 CRUD、前端初稿、测试模板和文档初稿方面显著提高了效率；但它在跨文件一致性、浏览器表单行为、状态保持和业务边界上出现过多次问题。本人通过运行测试、浏览器验收和局部修正完成了收口。这个过程让我认识到：AI 可以加速开发，但不能替代对数据模型、业务语义和系统边界的思考。

### 10.2 不足之处

1. 文件题目前只保存文件名或地址字符串，没有接入对象存储和真实上传。
2. 统计页主要面向常规问卷，复杂交叉分析和自定义报表还未实现。
3. 自动化测试以服务层和 API 层为主，浏览器端到端测试和并发测试不足。
4. 题目和问卷的版本管理、审计日志、回收站等生产级能力尚未加入。
5. AI 生成的初稿需要较多人工验收，提示词和任务拆分方式仍可继续优化。

### 10.3 后续改进

- 接入对象存储，实现真正的文件上传、预览和下载。
- 增加端到端测试，覆盖创建、发布、填写、统计的完整浏览器流程。
- 增加问卷版本号和变更记录，支持已发布问卷的结构审计。
- 增加更多统计维度，例如交叉分析、筛选条件和自定义导出字段。
- 使用 Docker 统一 MongoDB 与后端运行环境，降低环境差异。
- 继续完善 AI 使用规范：每次修改要求 AI 附带测试命令、影响文件和回滚说明。
